# 任务交接

## 适用范围

- “每单元”“转云端”“回本机”只用于走完整流程的任务；其他任务不建 `.handoff.md`。
- 只用流程一部分的任务如果生成了计划文档，在完成时执行“收尾”一节。
- `.handoff.md` 放在仓库根，结构见 `references/handoff-template.md`，只由主控写入，只提交在本任务的 feature 分支上，不记凭据和私人信息。
- 派活带看板摘录、异议和圆桌规则见 `dispatch`；提示词选用见 `prompt-library`。

## 每单元

1. 每个单元开始前，有 `quota-status` 命令时运行它查额度（`command -v quota-status` 找不到就跳过，不算错）。
2. 验收子任务。子任务自己不提交，所以主控先在它的工作树里把验收过的改动提交到它自己的分支，再把这个分支合进 feature 分支但先不提交（`git merge --no-ff --no-commit <子任务分支>`）；提交和推送只由主控执行。
3. 更新 `.handoff.md`：
   - 更新“状态表”。
   - 把本单元移入“已完成单元”，从“剩余单元”移除。
   - 把本单元在“执行者结论”中的记录压成一行。
   - 补入新增的用户原话（只记需求、更正和拍板，逐字；长材料只记出处）和已定决策（每条一行，含异议和圆桌结果）。
   - 同步更新“还没合回的子任务分支”和“欠下的审查”。
4. 把更新后的 `.handoff.md` 加进这次合并，和本单元代码作为同一个提交提交，推送到 feature 分支；推送成功才算这个单元完成。

## 转云端

仅在用户说“转云端”时执行。云端只用 Claude，跟随本机当前 org；账号需已在 claude.ai 连接 GitHub。

1. 有 `quota-status` 命令时运行它查当前 org 额度；受限或无额度时立即停止，不起云端会话，向用户说明原因。没有这个命令就跳过这一步，照常转。
2. 停掉所有运行中的 GPT 和 Gemini 子任务。
3. 逐个处理未合回的子任务工作树：把改动提交到它自己的分支并推送到远端；在 `.handoff.md` 的“还没合回的子任务分支”中写明对应单元、做到哪，并标为“未做完、未验收”。
4. 确认 `.handoff.md` 交接部分自足（含计划完成时的删除提交规则），提交并推送 feature 分支。
5. 清掉残留的信号分支：运行 `git ls-remote --exit-code origin refs/heads/<feature 分支名>-handback`，退出码 0 就 `git push origin --delete <feature 分支名>-handback`。删不掉，或查询失败（退出码不是 0 也不是 2），就停下向用户说明，不起会话。
6. 从 `orgs.json` 读取当前 org 对应的云端环境 ID。
7. 在仓库目录运行：
   `claude -p "<提示>" --environment <环境 ID> --output-format json`
   `<提示>` 中必须写明：
   - 先读仓库根的 `.handoff.md` 和其中的计划文档；
   - 切到并推送到 `.handoff.md` 指定的 feature 分支（不要只留在云端新建的 `claude/...` 分支）；
   - 每完成一个单元就更新 `.handoff.md` 并推送一次（原定给 GPT、Gemini 的单元改由 Claude 做，在“已完成单元”标明“改由 Claude 做”并记入“欠下的审查”；容器 30 分钟无新消息或满 8 小时会被回收，未推送改动会丢）；
   - 接着做完 `.handoff.md` 中“还没合回的子任务分支”列出的分支，验收后合回 feature 分支；
   - 若计划全部做完，按 `.handoff.md` 的规则用一个提交删掉本任务的计划文档和 `.handoff.md` 并推送；
   - 开工前在状态表末尾加一行接手记录，写明接手时 feature 分支的提交（起点提交），单独提交并推送，然后才开始第一个单元；
   - 每个单元的代码和更新后的 `.handoff.md` 放进同一个提交；
   - 每个单元开始前运行 `git ls-remote --exit-code origin refs/heads/<feature 分支名>-handback`。退出码 0 表示有信号：不再开新单元，先把手上的单元连同交接说明提交并推送，再在状态表末尾再加一行停机记录，写同一个起点提交和停下前 feature 分支的最新提交，单独提交并推送后停止；一个单元都没做完也照样写。退出码 2 表示没有信号，继续做。别的退出码是查询失败，重试，不当成没有信号；
   - 收到“立刻回”的消息时，先把做到一半的改动提交到一个单独的分支（不是 feature 分支）并推送，再在 feature 分支的交接说明里把这个分支记进“还没合回的子任务分支”、标为“未做完、未验收”，在状态表末尾再加一行停机记录，写同一个起点提交和停下前 feature 分支的最新提交，单独提交并推送后停止；一个单元都没做完也照样写；
   - 不开合并请求，不自动合并；
   - 不碰需要验证码的 VM。
8. 从输出 JSON 取出云端会话链接发给用户，记下会话 ID 供“回本机”使用。
9. 交接后本机不写 feature 分支和 `.handoff.md`，直到云端停下；这期间本机只在子任务工作树里干活。

## 回本机

有两种说法。信号分支名是 feature 分支名加 `-handback`，由本机建、本机删（云端不能删分支）。云端停下之前，本机不写 feature 分支和 `.handoff.md`。

### 用户说“回本机”

1. 推信号分支：`git push origin HEAD:refs/heads/<feature 分支名>-handback`。能给云端会话发消息时同时发一条，但不依赖它：
   `claude -p "<消息>" --cloud <会话 ID>`（来自文档，未实测）
2. 不干等：`git fetch` 后先看远端 feature 分支的最新提交是不是删掉本任务计划文档和 `.handoff.md` 的那个提交。是，说明计划已在云端做完，跳过并行单元，直接做“云端停下之后”。不是，就读远端最新的 `.handoff.md`，排除云端正在做的单元，从“剩余单元”的末尾往前挑一个依赖已满足、文件和排在最前面两个剩余单元不重叠的，在子任务工作树里先做（按 `dispatch` 派活），先不合回。挑不出就等。
3. 看云端停了没有：`git fetch` 后看远端 feature 分支的最新提交。两种情况算停：`.handoff.md` 的状态表里有本次停机记录（起点提交和状态表里最后一条接手记录相同的那条“已停”；更早的“已停”是上一次转云端留下的，不算）；或者最新提交就是删掉本任务计划文档和 `.handoff.md` 的那个提交（计划已在云端做完）。不开浏览器看云端日志用 `RemoteTrigger` 的 `get_run_log` 加会话 ID。云端没标明已停、而用户确认会话已结束时，以远端 feature 分支的最新提交为准。
4. 云端可能意外停掉（撞限额、容器被回收），那时它不会写停机记录。并行单元做完后（没挑出单元时，等满 30 分钟后；云端容器 30 分钟无新消息就会被回收）重新 `git fetch`：有新提交就记下最新的提交，继续等停机信号；连续两次检查（间隔 30 分钟）之间没有新提交，也没有本次停机记录或计划的删除提交，就问用户云端会话的状态。用户确认已结束后再拉取一次，以远端 feature 分支的最新提交为准，云端手上没推送的那个单元由本机重做。
5. 接着做“云端停下之后”。

### 用户说“立刻回”

1. 给云端会话发消息，要求它先把做到一半的改动提交到一个单独的分支（不是 feature 分支）并推送，再在 feature 分支的交接说明里把这个分支记进“还没合回的子任务分支”、标为“未做完、未验收”，在状态表末尾再加一行停机记录，写同一个起点提交和停下前 feature 分支的最新提交，单独提交并推送后停止；一个单元都没做完也照样写。
2. 持续 `git fetch`。远端出现本次停机记录，或最新提交已是计划的删除提交，才接手；在这之前本机不写 feature 分支，只在子任务工作树里干活。
3. 消息发不了，或发出后等满 30 分钟仍没有停机信号：请用户在 claude.ai 或手机上核实并停掉会话。用户确认已结束后再拉取一次，以远端 feature 分支的最新提交和交接说明里登记的半成品分支为准；没推送的那个单元由本机重做。
4. 做“云端停下之后”的第 1 到 6 步，再把那个未做完的分支做完、验收、合回，最后才发四行汇报。

### 云端停下之后

1. 在本机拉取远端 feature 分支到云端最后那个提交。
2. 信号分支存在就删掉：`git push origin --delete <feature 分支名>-handback`。
3. 读最新的 `.handoff.md`，核对已完成单元、剩余单元、未合回的子任务分支和“欠下的审查”。云端已做完计划并删掉了它时，从那个删除提交的前一个提交里读（`git show <删除提交>^:.handoff.md`）。
4. 本机先做的那个单元：核对它在交接说明里仍是剩余单元，再按“每单元”验收并合回；云端已经做了它就放弃本机这份。
5. 对交接点（状态表里最后一条接手记录的起点提交；云端没来得及推送接手记录就结束时，先对照云端日志和远端历史定出起点）之后到云端最后那个提交之间的全部云端提交补一轮 GPT 审查（按 `dispatch` 的审查规则执行）。
6. 原定由 Gemini 写、被 Claude 代写的文档，交给 Gemini 过一遍：它交回全文，主控落笔，并向用户列出改动。
7. 用正好四行向用户汇报：
   - 做完的：<云端和本机完成的单元与提交概要>
   - 等用户的：<需要用户拍板或介入的事项；没有写“无”>
   - 失败的：<失败、卡住或审查挡住的事项；没有写“无”>
   - 用量：<各次派活的模型和次数；有 `quota-status` 命令时加上它读出的额度概要>

## 收尾

1. 确认所有子任务分支都已合回 feature 分支或明确放弃。
2. 确认完成前审查已通过（走完整流程的任务必审；单点任务仅在改动碰到钱、权限、数据、对外消息或用户点名时审查；GPT 写的部分由 Claude 审）。
3. 在 feature 分支上用一个提交删除本任务的计划文档和 `.handoff.md`，不动其他计划文件；云端已经删过则跳过。
4. 在本机删除已合回的子任务分支（云端不能删分支）。
5. 推送 feature 分支。
6. 把计划摘要留作合并请求描述，问用户是否开合并请求、从哪个分支合到哪个分支（建议压缩合并）。不自动开合并请求，不自动合并。

## 手机续跑

没来得及说“转云端”就合盖时使用；每单元都已推送，最多丢正在做的那个单元。

1. 起会话前先看远端有没有残留的信号分支 `<feature 分支名>-handback`（在 GitHub 的分支列表里看）。有就先删掉；云端会话删不了分支，要在 GitHub 上或本机删。删不掉就先不起会话，等回到电脑再处理。
2. 在 Claude 手机端新建云端会话。
3. 选择对应 org 的云端环境和本任务的 feature 分支。
4. 发送：`按 .handoff.md 继续`。
5. 回到电脑后按“回本机”接回。云端照 `.handoff.md` 里写的规则每单元推送、检查信号分支。

## 看板

用户说“看板”时执行。

- 在 T3 Code 中：读取 `.handoff.md` 的状态表和最近的已定决策，现场生成一页 HTML，调用 `html_preview` 和 `html_render` 渲染成一页图展示给用户，不存模板文件。
- 在终端中：直接打印 `.handoff.md` 的状态表。
