## 多模型分工

- 直接收到用户的任务时你是主控；收到派活单时你是执行者，以派活单为准，以下规则不适用。
- 先选路：直接答或直接做（几十行以内、原因清楚的小改动）；交给合适的主执行者；只用流程的一部分；完整流程。从最轻的开始，任务变大就升档并用一句话告诉用户；用户一句话可以改档。
- 主执行者按专长：文档、文案、润色、翻译、点子归 Gemini；审代码、难 Bug、后端、算法、数据处理、性能、运维排查、浏览器多步操作、大调研归 GPT；界面、视觉、动效、读懂代码库、架构取舍归 Claude。交给别家时只转交用户原话和材料、核实结果，不改写；GPT 的结论转述成好读的话。
- 派子任务前依次判断：要不要派、按任务类型取默认模型、按大小和风险调档、按额度走备选链。执行默认用 Opus 5.5、GPT Sol、Gemini；单元难、风险高，或默认档第一次没做对，才升到 Fable 或 GPT Astra，并用一句话告诉用户。表和派活单模板在 `dispatch` skill。
- 思考深度默认 medium；查找和调研可降到 low；审查碰到钱、权限、数据、对外消息时可升到 high；GPT Astra 做方案和文档可用 high，写代码用 medium。
- 只有主控提交和推送。完整流程里每完成一个单元，代码和更新后的 `.handoff.md` 放进同一个提交再推送，做法见 `task-handoff` skill。
- 完整流程在宣布完成前和开合并请求前审一轮：默认 GPT 审，GPT 写的由 Claude 审。单点任务（含直接做的）只在碰到钱、权限、数据、对外消息或用户点名时审。只有说得出怎么发生的严重问题才挡住，其余记为建议。最多两轮：第一轮谈不拢，第二轮只问还没参与的那一家；两轮不过交用户定。
- 审查通过后问用户是否开合并请求、从哪个分支合到哪个分支。不自动开，不自动合并。
- 每个单元开始前，有 `quota-status` 命令时运行一次（`command -v quota-status` 找不到就跳过，不算错）；它显示省额度模式时，主控只做调度和验收，执行改派。它打印“建议换到”时先换 org 再开工：终端里用 `/org switch`，T3 Code 里把本线程切到它写的那个实例，做法见 `dispatch` skill。
- 在 T3 Code 里用 T3 的派活、工作树和合并请求工具；在终端里用 compound-engineering 的跨模型通道。
- 走到计划、文档评审、开工时分别用 `ce-brainstorm`（可选）、`ce-plan`、`ce-doc-review`、`ce-work`，只开必要的子任务。
- 团队协作：派活带看板摘录，执行者可以先提异议，圆桌只在三种情况开：难以撤回且各方案代价差别大的决定、审查第一轮谈不拢、用户点名。做法见 `dispatch` skill。
- 提示词：每个任务从 `prompt-library` skill 挑 0 到 3 条，并用一句话说明。
